五、实施步骤 B：提示词与响应解析

Generator 接收原题和公开执行约定，生成完整可执行 Python 模块，
包含必要 imports、所有要求的函数和辅助函数，不仅是 entry_point 的
函数体。例如 MagicSquareGame/2.6 同时要求 Alice/Bob 两个函数。
要求一次返回：
  {"code": "完整 Python 源码", "p_correct": 0.0}
其中 p_correct 的含义是该代码通过固定版本官方 checker 的概率。

Verifier 接收原题、公开执行约定、同一份冻结程序，返回：
  {"p_correct": 0.0}
它只判断既定候选；不生成替代代码，不读取其他 verifier，不接收
generator r、模型名称、参考解、test 源码或 checker 结果。
评估端和数据收集端的物理/模块边界应支持这一信息限制。

解析规则应在调用模型前固定：
- 使用完整 JSON 解析，不用最短花括号正则截取（代码中有字典和括号）。
- 拒绝重复 JSON 键、NaN/Infinity、布尔概率和越界概率；保留原始输出。
- 可决定只允许 JSON，或允许恰好一层完整 JSON markdown fence；选定
  后写入 prompt_version，不在看到失败输出后临时放宽或修复。
- 不从 thinking/reasoning 段抽取答案，只解析 provider 的最终文本。
- 代码字符串明确且可提取时即保存；语法错误代码也交官方 checker，
  不由 AST 检查提前删题或替代官方标签。
- 代码有效字段与 confidence 分别记录：有代码但 r 无效时可保存官方
  结果，但顺序策略因无初始概率而弃答，不自行填 0.5。
- 无可提取代码时记录 generator format failure，不伪造官方调用或
  official_passed；端到端完成率/任务通过率统计中明确计入失败分母。
- 不自动重生成、修复代码或请求模型补 JSON。verifier 格式失败记录
  missing signal，顺序模式依现有失败策略弃答，不当作概率零。

尚未取得官方返回值的服务中断才是 missing/unresolved，不捏造标签。

每个冻结候选一次官方评估，持久化后恢复时复用：
- key 至少绑定 task_id、candidate/code hash、checker/test hash 和环境。
- 先记录运行意图，再运行并持久化结果；已完成结果不重跑。
- 如 worker 已执行但结果丢失，标记 unresolved，不能自动再抽一次随机
  结果并假装是原结果。诊断性重跑必须另记，不能取代主标签。
- 不更改官方随机行为，也不把 CHSH 30 次诊断的多数结果用于打标签。
- 外层 supervisor 应给官方 30 秒计时留启动/回收余量；若外层自身
  超时未获得官方返回，按服务异常记录，不能伪称官方 Timeout。

参考审计使用的 venv + subprocess 不是运行任意生成代码的安全边界。
模型代码应在隔离 worker/container 中执行：无 ADC/云凭据、禁网、
不挂载用户主目录或整个仓库、固定依赖，并限制内存、进程和运行时间。
这属于执行环境约束，不增加自定义语义判题。记录资源上限及平台。

七、实施步骤 D：缓存、调用流程与顺序适配

所有 LLM 调用使用现有 RequestCache / BudgetedRequestCache；记录
真实 provider response、模型版本、token usage、延迟、费用估算。
不确定的付费请求不自动重发；沿用已有 transport 的恢复规则。
BudgetedRequestCache 已对明确 HTTP 429 拒绝做有界退避，不要再叠加
一个宽泛的异常重试循环。缓存命中和新增付费执行分别计数。

本 pilot 默认每题一次 generator、三个配置化 verifier，先不要多样本
生成。同一冻结代码发给各 verifier，严格不让后一个看到前一个结果。
有代码时可收集开发诊断信号，即使 r 无效；但顺序策略仍须按无 prior
弃答，报表分别列出有代码/有 r/有标签/有 verifier 的样本数。

开发收集与顺序执行是两个明确模式：
1. collect-development：收集全部 verifier 概率，用于接口、分布和
   缺失率检查；实际调用费用全部计入，不能说这些调用被策略省掉。
2. run-sequential：接受已冻结 policy 和公共候选，由策略决定是否
   query；只有决定后才请求或读取对应缓存信号。停止后不访问未来
   verifier 或标签，checkpoint 恢复不得重复请求。
   本轮用合成 policy / fixtures 验证接口，标为工程 dry run；不把
   GPQA 已拟合的 likelihood 直接作为 QuantumKatas 的正式参数。

复用 NestedPlanner 的数值核心，可参考 sequential.py 的恢复语义，
但适配 code candidate 的有效性和 prompt。无需重写论文算法。
未来在校准数据足够时，再按原方法拟合新领域的 prior/likelihood。
全信号数据的 replay 可以作为开发演示，但只能报告模拟逻辑查询量，
不能当成实际省下的 API 账单，也不能报告同批拟合/评分为独立验证。

注意现有 common/api.request_key 绑定 runner identity + prompt + system，
不绑定 Request.key/meta 中的 task_id 或 generation_id。第一轮只生成
一次即可；未来若做多次独立采样，不能只改 meta 就把缓存命中算成
新样本，也不能为此破坏已有 GPQA 缓存身份。
